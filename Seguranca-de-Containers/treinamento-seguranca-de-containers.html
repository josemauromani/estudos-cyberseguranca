Seção 01

Introdução: A Falha Era na API, o Estrago Foi no Servidor

Na Ipê Store, a API de pedidos roda num container no servidor DOCKER-01. Uma dependência desatualizada permitiu execução remota de código, e o invasor ganhou um shell dentro do container. Até aí, o estrago deveria ficar contido: um processo sem privilégio, num sistema de arquivos descartável. Só que o time tinha montado o socket do Docker no container "para a API reiniciar o worker de e-mails", e o container rodava como root com --privileged. Em minutos o invasor controlava o servidor inteiro e os outros seis containers que rodavam nele. A vulnerabilidade era da aplicação; o que transformou um incidente pequeno em um grande foi a configuração do container. Este módulo ensina a ler um Dockerfile e um docker run como um auditor e a fechar o que separa o container do host.

O que separa um container comprometido do servidor que o hospeda?

🧭 Diferença para o Estudo 22 e o que vem do Estudo 34

O Estudo 22 cobriu o pipeline: SAST, DAST, SCA, a varredura da imagem como um portão do CI e a assinatura com Cosign em poucas linhas. Aqui o foco desce para a própria imagem (camadas, base, usuário, origem), para o registro e para o tempo de execução: o que cada opção do docker run devolve de poder ao processo. Do Estudo 34 vêm usuários, permissões, processos e o UID 0; aqui você verá como o kernel do Linux separa um processo do resto do sistema e o que acontece quando essa separação é desligada.

Container não é máquina virtual

Uma máquina virtual tem o próprio kernel, isolado pelo hipervisor. Um container é só um processo comum do host, com uma visão restrita do sistema: o kernel compartilhado é o mesmo para todos os containers e para o host. O isolamento vem de recursos do kernel que o runtime (Docker, containerd, Podman) liga ao criar o processo. Cada camada desliga um tipo de acesso; nenhuma, sozinha, é uma fronteira completa.

MecanismoO que fazO que desliga a proteção
namespacesDão ao processo a própria visão de PIDs, rede, montagens, hostname, IPC e usuários--pid=host, --network host, volumes do host
cgroupsLimitam CPU, memória e número de processos (--memory, --pids-limit)Ausência de limites: um container esgota o host
capabilitiesDividem o poder do root em pedaços (NET_ADMIN, SYS_ADMIN, SYS_PTRACE...); o Docker já remove várias por padrão--cap-add, --privileged
seccompFiltra chamadas de sistema perigosas com um perfil padrão--privileged, --security-opt seccomp=unconfined
AppArmor / SELinuxPolítica de acesso obrigatória sobre arquivos e operações--privileged, perfil desativado
Usuário não rootO processo não é UID 0; com rootless ou userns-remap, nem o root do container é root no hostDockerfile sem USER, --user 0
Barreiras entre o Container e o Host Mermaid

No MITRE ATT&CK, duas técnicas resumem o risco: T1610 Deploy Container (o adversário cria um container para executar código ou contornar defesas, tipicamente por uma API do daemon exposta) e T1611 Escape to Host (sair do container para o host). Quase todo caminho de saída depende de uma configuração que você controla: privilégio a mais, socket montado, namespace do host compartilhado. A NIST SP 800-190 (Application Container Security Guide) e o CIS Docker Benchmark organizam essas recomendações em imagem, registro, orquestrador, container e host.

Seção 02

Imagem, Build, Registro e Runtime

Camadas: segredos nunca em camadas da imagem

Cada instrução RUN, COPY e ADD gera uma camada imutável, e ENV e ARG ficam registrados nos metadados. Apagar um arquivo num passo seguinte só cria outra camada que o esconde: o conteúdo continua extraível da camada anterior. O comando docker history mostra os comandos e argumentos de build de qualquer imagem que você conseguiu puxar. Por isso um token em ENV, uma senha em ARG ou um .npmrc copiado vazam para todo mundo que tem acesso à imagem: registro, cache do CI, backup.

bash — o que a imagem conta sobre si mesma (saída ilustrativa) 
$ docker history --no-trunc docker.io/ipestore-dev/api-pedidos:latest
CREATED BY
CMD ["node" "server.js"]
COPY . .
RUN npm ci --omit=dev && rm -f .npmrc        # o .npmrc continua na camada de baixo
COPY .npmrc package.json package-lock.json ./
ENV NPM_TOKEN=npm_LAB0ficticio0000000000000000   # token legível por qualquer um
...

# Segredo de build do BuildKit: o arquivo existe só durante o comando, em nenhuma camada
RUN --mount=type=secret,id=npmrc,target=/app/.npmrc npm ci --omit=dev
$ docker build --secret id=npmrc,src=$HOME/.npmrc -t api-pedidos .

Se um segredo já foi publicado numa imagem, a correção não é só um Dockerfile novo: revogue a credencial, porque as imagens antigas continuam nos registros e caches. Liste .env, .npmrc, .git e chaves no .dockerignore: um COPY . . copia tudo o que não estiver lá.

Imagem mínima, usuário não root e tag fixa

  • Base mínima e distroless: uma imagem completa (node:20, python:3.12) traz shell, gerenciador de pacotes, compiladores e centenas de pacotes. As variantes -slim e alpine cortam boa parte; as imagens distroless trazem só o runtime da linguagem, sem shell. Menos pacotes significa menos vulnerabilidades na varredura e menos ferramentas para quem invadir.
  • Build multiestágio: compile e instale dependências num estágio com o toolchain completo e copie só o resultado para um estágio final mínimo. O compilador do Go ou o npm nunca chegam à produção.
  • USER não root: declare um UID numérico no estágio final. Mesmo quando a base já define usuário (distroless :nonroot), deixar USER explícito facilita auditoria e as políticas que exigem runAsNonRoot.
  • Tag vs digest: a tag é um rótulo mutável; o digest (@sha256: seguido de 64 caracteres hexadecimais) identifica exatamente um conteúdo. Fixe a base pelo digest e deixe um robô (Renovate, Dependabot) abrir o pull request de atualização, que passa pela varredura.
  • Origem do que entra no build: ADD https://... e curl ... | sh confiam no servidor no momento do build. Use ADD --checksum=sha256:... ou confira o hash antes de instalar.
Dockerfile — build multiestágio da vitrine (Go) com distroless 
# Estágio 1: compila com o toolchain completo do Go
FROM golang:1.23.2-bookworm@sha256:<digest-conferido> AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/vitrine ./cmd/vitrine

# Estágio 2: só o binário, sem shell nem gerenciador de pacotes
FROM gcr.io/distroless/static-debian12:nonroot@sha256:<digest-conferido>
COPY --from=build /out/vitrine /vitrine
USER 65532:65532
ENTRYPOINT ["/vitrine"]

Varredura de imagem: ler o relatório e priorizar

Ferramentas como Trivy e Grype comparam os pacotes da imagem (do sistema e da linguagem) com bases de vulnerabilidades. O relatório de uma imagem completa costuma ter centenas de linhas, e corrigir na ordem do CVSS desperdiça esforço. Leia cada achado com quatro perguntas: há versão corrigida? Está no catálogo KEV da CISA (já explorada)? Qual o EPSS (probabilidade de exploração em 30 dias, da FIRST)? O pacote é da base ou da aplicação? Vulnerabilidades da base somem em bloco quando você troca para uma base mínima; as da aplicação só saem atualizando a dependência (SCA, Estudo 22). Sem correção publicada, registre o aceite com prazo e mitigação (Estudo 9).

Assinatura e registro confiável

O projeto Sigstore, com o Cosign, assina a imagem no pipeline (com chave ou keyless, via identidade OIDC e registro de transparência); o Notation, do projeto Notary, é a alternativa no ecossistema OCI. Assinar não basta: quem roda precisa verificar, e verificar a mesma imagem que vai rodar. Restrinja também a origem: só imagens do registro da empresa, alimentado pelo pipeline, e nada de contas pessoais em registros públicos. Em Kubernetes, uma política de admissão aplica as duas regras (Estudo 51).

Runtime: o que o docker run devolve ao processo

bash — implantação endurecida da API de pedidos 
# verifique e rode pelo mesmo digest: a tag pode apontar para outra imagem entre os dois comandos
cosign verify --key cosign.pub registry.ipestore.example/loja/api-pedidos@sha256:<digest-conferido>
docker run -d --name api-pedidos \
  --read-only --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --memory 512m --pids-limit 200 \
  -p 3000:3000 \
  registry.ipestore.example/loja/api-pedidos@sha256:<digest-conferido>
🚨 --privileged e docker.sock abrem caminho ao host

--privileged devolve todas as capabilities, libera os dispositivos do host e desliga seccomp e AppArmor: o container deixa de ser fronteira. Montar /var/run/docker.sock é pior, porque nem precisa de falha no isolamento: o socket é a API do daemon, que roda como root, e quem fala com ele cria o container que quiser. Nos dois casos, uma falha na aplicação vira controle do host. Trate ambos como achados críticos, sempre.

Para reduzir o impacto mesmo quando algo escapar, rode o daemon em modo rootless ou com userns-remap: o UID 0 dentro do container passa a ser um UID sem privilégio no host.

Detecção em runtime

Prevenção falha; o que sobra é perceber rápido. Ferramentas como Falco (CNCF) observam chamadas de sistema dos containers e alertam sobre comportamentos que uma aplicação não deveria ter: shell interativo num container de API, gravação em /etc, acesso ao docker.sock, criação de container privilegiado. O alerta vai para o SIEM e entra no fluxo da Trilha 11.

YAML — regra Falco: shell em container de aplicação (simplificada) 
- rule: Shell em container da loja
  desc: Um shell iniciado num container de aplicação da Ipê Store
  condition: >
    spawned_process and container
    and proc.name in (sh, bash, ash)
    and container.image.repository startswith "registry.ipestore.example/loja/"
  output: "Shell em container (imagem=%container.image.repository usuario=%user.name cmd=%proc.cmdline)"
  priority: WARNING
  tags: [container, mitre_execution]

Seção 05

Questões de Fixação e Entrevista

Questão 1 (Segredo em camada): Um desenvolvedor percebeu um token em ENV, apagou a linha e publicou a imagem nova com a mesma tag. O problema acabou?
Ver resposta explicada

Resposta: Não. As imagens antigas continuam no registro, nos caches do CI e nas máquinas que já as puxaram, e qualquer uma delas mostra o token nos metadados e no docker history. O primeiro passo é revogar o token e emitir outro; depois, passar o segredo pelo BuildKit (--mount=type=secret) ou em tempo de execução, e varrer o histórico do registro em busca de outras versões expostas.

Questão 2 (docker.sock): O time diz que montar o docker.sock é seguro porque o container roda com usuário não root e sem --privileged. Você concorda?
Ver resposta explicada

Resposta: Não. O socket é a API do daemon Docker, que roda como root no host; quem consegue escrever nele pede ao daemon um container novo com qualquer configuração. As restrições do container original não valem para o que o daemon cria. Se a aplicação precisa reiniciar outro serviço, use o orquestrador com permissão mínima ou uma fila; ferramentas que exigem o daemon ficam isoladas e monitoradas (T1610).

Questão 3 (Priorização): A varredura mostra uma crítica sem correção no ImageMagick da base, que a aplicação não usa, e uma alta corrigível numa biblioteca de token da aplicação, presente no KEV. Qual vem primeiro?
Ver resposta explicada

Resposta: A da biblioteca de token: está sendo explorada, tem correção e fica no caminho de autenticação da API. A crítica sem correção entra em aceite com prazo, e a melhor mitigação é sair da base completa: numa base mínima ou distroless o pacote nem existe. CVSS sozinho não ordena a fila; KEV, EPSS, existência de correção e origem do pacote, sim.

Questão 4 (Capabilities): Para depurar um travamento, um analista acrescentou --cap-add SYS_ADMIN e --pid=host ao gerador de relatórios. O problema foi resolvido, mas a configuração ficou. Por que isso é grave?
Ver resposta explicada

Resposta: SYS_ADMIN concentra tanta coisa que equivale quase a --privileged, e --pid=host faz o container enxergar todos os processos do host. Juntos, desmontam duas camadas de isolamento de um serviço que lê arquivos externos. Depuração é feita num container temporário, aprovado e removido em seguida; a configuração de produção volta ao --cap-drop ALL.

Questão 5 (Tag e digest): O Dockerfile usa FROM python:3.12. Um colega diz que isso já é "versão fixa". O que falta?
Ver resposta explicada

Resposta: A tag 3.12 é republicada a cada correção do Python e do Debian: dois builds do mesmo Dockerfile podem usar bases diferentes. Fixar o digest (@sha256:) torna o build reprodutível e auditável; a atualização vira um pull request automático que passa pela varredura antes de entrar. Vale também trocar para a variante slim ou para um estágio final distroless.

Questão 6 (Assinatura): O pipeline assina todas as imagens com Cosign, mas o servidor roda docker run direto da tag, sem verificar nada. A assinatura protege alguma coisa?
Ver resposta explicada

Resposta: Quase nada. Assinatura só vale se alguém verifica antes de rodar, e verifica a mesma imagem que vai rodar. Sem cosign verify (ou uma política de admissão no Kubernetes), uma credencial de push vazada basta para pôr uma imagem adulterada em produção. Some a isso a restrição de origem: só o registro da empresa.

Questão 7 (Detecção): A imagem da API é distroless, sem shell. Ainda faz sentido uma regra Falco de "shell em container"?
Ver resposta explicada

Resposta: Sim, e com alta confiança: se um shell aparecer num container que não tem shell, alguém o trouxe. A regra quase não gera falso positivo nessas imagens e cobre também os containers legados que ainda usam base completa. Detecção em runtime é a camada que funciona quando a prevenção falhou.

Seção 06

Fatos Essenciais, Referências e Próximos Passos

1. Imagem

Imagem mínima, usuário não root e tag fixa, com o digest conferido e build multiestágio.

2. Camadas

Segredos nunca em camadas da imagem: apagar depois não remove, e o segredo exposto deve ser revogado.

3. Runtime

--privileged e docker.sock abrem caminho ao host; comece de cap-drop ALL e somente leitura.

4. Origem

Assinatura e registro confiável: assinar no pipeline e verificar a imagem que realmente vai rodar.

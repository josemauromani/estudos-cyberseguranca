Seção 01

Introdução: Onde os Dados Realmente Moram

Firewall, EDR e WAF protegem o caminho. O alvo final quase sempre é o banco de dados: cadastro de clientes, pagamentos, segredos de aplicação. Em boa parte dos vazamentos, o atacante não quebra o banco; ele usa uma conta que já tinha permissão demais. Este módulo ensina a dar a cada usuário só o que ele precisa, registrar quem fez o quê e proteger os dados mesmo quando alguém chega até eles.

Revisão Rápida do Modelo Relacional

Um banco relacional guarda dados em tabelas ligadas por chaves: a chave primária identifica cada linha e a chave estrangeira aponta para a linha de outra tabela (por exemplo, pedidos.cliente_id aponta para clientes.id). O JOIN junta essas tabelas numa consulta. As transações seguem as propriedades ACID: Atomicidade (tudo ou nada), Consistência (regras do esquema sempre válidas), Isolamento (transações concorrentes não se enxergam pela metade) e Durabilidade (o que foi confirmado sobrevive a uma queda).

Seção 02

Menor Privilégio, Auditoria e Proteção dos Dados

Roles, GRANT e REVOKE

Permissões se concedem a roles (papéis), não a pessoas. Cada usuário recebe o role da sua função, e o role recebe só os privilégios necessários em cada tabela. Os exemplos usam PostgreSQL; os quadros de equivalência mostram SQL Server e MySQL.

Menor privilégio com roles (PostgreSQL) 
-- 1. Ninguém herda nada por padrão
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM PUBLIC;

-- 2. Um role por função, sem login
CREATE ROLE analista_bi NOLOGIN;
GRANT USAGE ON SCHEMA public TO analista_bi;
GRANT SELECT ON clientes, pedidos, produtos TO analista_bi;

-- 3. O usuário só ganha o role
CREATE ROLE joao LOGIN PASSWORD 'troque-esta-senha';
GRANT analista_bi TO joao;

-- 4. Retirar um privilégio concedido a mais
REVOKE SELECT ON pagamentos FROM analista_bi;
⚠️ O role PUBLIC e a mudança do PostgreSQL 15

Todo role é membro implícito de PUBLIC, então um privilégio dado a PUBLIC vale para todos. Até a versão 14, qualquer usuário podia criar objetos no esquema public. A partir do PostgreSQL 15, esse privilégio CREATE deixou de ser concedido a PUBLIC por padrão. Bancos migrados de versões antigas podem manter o comportamento antigo: confira.

Views e Row-Level Security

Uma view expõe só as colunas necessárias: o BI pode ler vw_clientes_bi com cidade e data de cadastro, sem enxergar CPF. A Row-Level Security filtra linhas: cada atendente vê apenas os clientes da sua região, mesmo consultando a mesma tabela.

View de colunas e política de linhas (PostgreSQL) 
CREATE VIEW vw_clientes_bi AS
  SELECT id, cidade FROM clientes;
GRANT SELECT ON vw_clientes_bi TO analista_bi;

ALTER TABLE clientes ENABLE ROW LEVEL SECURITY;
CREATE POLICY clientes_da_regiao ON clientes
  FOR SELECT TO atendimento
  USING (cidade = current_setting('app.cidade_atendente'));

Contas de Serviço

A aplicação acessa o banco com uma conta de serviço. Ela não deve ser dona das tabelas, não deve ter DELETE se o sistema só faz exclusão lógica, e nunca deve ter privilégios de DDL. Senha em cofre de segredos, rotação periódica e origem restrita por IP fecham o resto.

Auditoria de Banco

  • pgAudit (PostgreSQL): extensão que registra leituras, escritas, DDL e mudanças de role no log do servidor.
  • SQL Server Audit: auditoria nativa no nível do servidor e do banco, com destino em arquivo ou no log de eventos do Windows.
  • MySQL: plugins de auditoria (o Enterprise Audit da Oracle ou alternativas de terceiros).
  • Database Activity Monitoring (DAM): ferramentas que observam o tráfego do banco em tempo real, alertam sobre padrões anômalos (como um SELECT * de madrugada na tabela de clientes) e guardam a trilha fora do alcance do administrador do banco.
Ativar pgAudit (postgresql.conf) 
shared_preload_libraries = 'pgaudit'
pgaudit.log = 'write, ddl, role'
pgaudit.log_relation = on

-- Depois de reiniciar o serviço:

Proteção dos Dados em Repouso

  • TDE (Transparent Data Encryption): cifra os arquivos do banco no disco sem mudar a aplicação. É nativo no SQL Server e no Oracle; no MySQL existe a criptografia de tablespace do InnoDB com keyring. O PostgreSQL comunitário não tem TDE nativo: usa-se criptografia de disco ou distribuições comerciais.
  • Criptografia de coluna: protege campos específicos, como CPF, mesmo para quem lê a tabela. No PostgreSQL, com a extensão pgcrypto (por exemplo, pgp_sym_encrypt). O ponto crítico é onde a chave fica guardada.
  • Dynamic Data Masking (mascaramento dinâmico): mostra o dado mascarado para quem não tem permissão de ver o valor real. É nativo no SQL Server; no PostgreSQL, usa-se uma view ou uma extensão como o PostgreSQL Anonymizer.
  • Backups cifrados: o backup tem os mesmos dados do banco e precisa da mesma proteção, inclusive fora do ambiente de produção.

SQL Injection e Prepared Statements

Concatenar texto do usuário na consulta permite que ele reescreva o SQL. A defesa principal são as consultas parametrizadas (prepared statements): o banco recebe o comando e os valores separados, e o valor nunca vira código. O módulo 12 (OWASP Top 10 Web) aprofunda o ataque.

Vulnerável vs parametrizado (Python com psycopg) 
# VULNERÁVEL: o e-mail digitado vira parte do SQL
# entrada maliciosa: ' OR '1'='1
cur.execute("SELECT id, nome FROM clientes WHERE email = '" + email + "'")

# CORRETO: o valor vai separado do comando
cur.execute("SELECT id, nome FROM clientes WHERE email = %s", (email,))

      Seção 05

      Questões de Fixação e Concursos

      Questão 1 (Sublinguagens SQL): Os comandos GRANT e REVOKE pertencem a qual sublinguagem do SQL?
      Ver resposta explicada

      Resposta: DCL (Data Control Language).

      DDL define a estrutura (CREATE, ALTER, DROP), DML manipula dados (SELECT, INSERT, UPDATE, DELETE) e TCL controla transações. Permissões são DCL.

      Questão 2 (Menor privilégio): A conta de serviço da aplicação é dona de todas as tabelas. Qual é o principal risco?
      Ver resposta explicada

      Resposta: Uma falha na aplicação, como SQL injection, passa a ter poder de dono: apagar tabelas, alterar a estrutura e conceder privilégios.

      O dono do objeto tem todos os privilégios sobre ele. A conta da aplicação deve ter só o DML de que o sistema precisa; a estrutura muda por um processo de migração separado.

      Questão 3 (Row-Level Security): Cada atendente deve ver apenas os clientes da sua região, consultando a mesma tabela. Qual recurso resolve isso no PostgreSQL?
      Ver resposta explicada

      Resposta: Row-Level Security, com ALTER TABLE ... ENABLE ROW LEVEL SECURITY e CREATE POLICY.

      GRANT controla o acesso à tabela inteira; views limitam colunas. A política de linha aplica um filtro automático em toda consulta do role.

      Questão 4 (TDE): Um auditor afirma que, com TDE ativo, o DBA não consegue ler os CPFs da tabela de clientes. Ele está certo?
      Ver resposta explicada

      Resposta: Não.

      O TDE protege os arquivos em disco e as mídias de backup contra roubo físico. Para quem consulta o banco com permissão, os dados aparecem em claro. Para esconder valores de usuários autorizados a ler a tabela, são necessários criptografia de coluna ou mascaramento.

      Questão 5 (SQL Injection): Um desenvolvedor propõe escapar aspas simples no campo de e-mail para evitar SQL injection. Qual é a defesa recomendada pela OWASP?
      Ver resposta explicada

      Resposta: Consultas parametrizadas (prepared statements).

      Escapar caracteres manualmente é frágil e depende do banco e da codificação. Com parâmetros, o valor nunca é interpretado como SQL. Menor privilégio na conta da aplicação limita o dano caso algo escape.

      Seção 06

      Fatos Essenciais, Referências e Próximos Passos

      1. Privilégio por role

      Usuários recebem roles; roles recebem só o necessário; nada vai para PUBLIC.

      2. Colunas e linhas

      Views limitam colunas, Row-Level Security limita linhas, mascaramento esconde valores.

      3. TDE não é tudo

      TDE protege o disco; quem consulta com permissão vê os dados em claro.

      4. Trilha de auditoria

      pgAudit, SQL Server Audit e DAM respondem quem leu e alterou o quê, e quando.

Seção 01

Introdução: A Requisição Perfeita que Não Deveria Passar

O aplicativo da Ipê Store, o site e os parceiros conversam com a mesma API. Um firewall vê requisições bem formadas, com token válido, para endpoints que existem; ele não tem como saber que o pedido 1043 não é da Ana, que o campo papel não deveria ser editável ou que vinte tentativas de login por segundo não são um cliente esquecido. Em APIs, as falhas mais graves são de lógica de autorização, e só a própria API pode barrá-las. Este estudo continua o Estudo 12, que mostrou o BOLA numa página web.

Seção 02

Tokens, Autorização em Três Níveis e Limites de Consumo

JWT: decodificar não é validar

Um JWT tem três partes em Base64URL: cabeçalho, carga (as claims) e assinatura. Qualquer um decodifica as duas primeiras; o que garante que ninguém mexeu nelas é a assinatura. A API precisa:

  • aceitar só os algoritmos esperados: um token com "alg": "none" não tem assinatura e deve ser recusado;
  • verificar a assinatura com a chave certa (segredo forte no HMAC ou chave pública no RS256/ES256);
  • conferir exp (validade), aud (a API a que o token se destina) e iss (quem emitiu).

Ler o papel do usuário de um token que só foi decodificado, sem validação, é o mesmo que perguntar ao atacante se ele é administrador: decodificar não é validar.

Autorização em três níveis

  • Objeto (API1, BOLA): o recurso pedido pertence ao usuário? Cada endpoint que recebe um ID confere.
  • Propriedade (API3): na entrada, uma allowlist de campos editáveis impede o mass assignment (mandar "papel": "admin" junto com o telefone); na saída, a mesma ideia evita a exposição excessiva de dados, como devolver o hash de senha "porque o front-end filtra".
  • Função (API5, BFLA): o papel do usuário pode chamar este endpoint? Rotas de administração escondidas não estão protegidas.

Validar a requisição contra um esquema (OpenAPI ou JSON Schema) com campos desconhecidos recusados resolve o mass assignment e ainda barra tipos e tamanhos inesperados.

Inventário: a /v1 zumbi

A /v2 foi corrigida, mas a /v1 continua no ar "para o app antigo", com o código de três anos atrás. APIs sombra (que ninguém documentou) e zumbi (que deveriam ter morrido) são a categoria API9: mantenha um inventário de versões e endpoints, com dono e data de desativação.

janela deslizanteConta as requisições do último segundo, a cada instanteGuarda o histórico de cada cliente

Requisições acima do limite recebem 429 Too Many Requests com o cabeçalho Retry-After. Limite por usuário, por IP e por operação: o login e a recuperação de senha precisam de limites bem menores que a listagem de produtos.

GraphQL e REST

Num GraphQL, um único endpoint aceita consultas montadas pelo cliente. Os cuidados mudam: desative a introspecção em produção, limite a profundidade e o custo das consultas (amigos de amigos de amigos derrubam o banco) e trate o batching, que coloca centenas de operações numa só requisição HTTP e passa por baixo de um rate limit que conta requisições. A autorização por objeto continua sendo responsabilidade de cada resolver.

python — validação de token, allowlist de campos e checagem de função 
# Token: algoritmo fixo, assinatura, exp, aud e iss conferidos pela biblioteca
claims = jwt.decode(token, CHAVE, algorithms=["HS256"],
                    audience="api.ipestore.example", issuer="https://auth.ipestore.example")

# Propriedade: só estes campos podem ser editados pelo próprio usuário
EDITAVEIS = {"nome", "telefone"}
recusados = set(corpo) - EDITAVEIS
if recusados:
    abort(422, {"erro": "campos não permitidos", "campos_recusados": sorted(recusados)})

# Saída: devolve só os campos públicos, nunca o registro inteiro
return {k: usuario[k] for k in ("nome", "email", "telefone")}

# Função: endpoint de administração exige o papel certo
if claims["papel"] != "admin":
    abort(403)

Respostas de parceiros e de serviços de terceiros são entrada externa: valide o esquema, limite o tamanho, use TLS e não siga redirecionamentos às cegas. Um parceiro comprometido vira a porta de entrada.

    Seção 05

    Questões de Fixação e Entrevista

    Questão 1 (WAF): Por que um WAF dificilmente detecta um ataque de BOLA?
    Ver resposta explicada

    Resposta: Porque a requisição é perfeitamente válida: token legítimo, endpoint existente, ID numérico. O que está errado é a relação entre o usuário e o objeto, que só a API conhece.

    Questão 2 (JWT): A API lê o papel do usuário com uma função que só decodifica o JWT. Qual o problema?
    Ver resposta explicada

    Resposta: Qualquer um pode alterar a carga do token (trocar "cliente" por "admin") ou mandar um token com alg: none. Sem verificar a assinatura, a API aceita o papel que o atacante escolher.

    Questão 3 (Mass assignment): O endpoint de perfil aceita o JSON inteiro e grava no banco. O que pode dar errado?
    Ver resposta explicada

    Resposta: O usuário manda campos que não deveria controlar, como papel ou credito, e eles são gravados. A correção é uma allowlist de campos editáveis, de preferência num esquema estrito.

    Questão 4 (Rate limit): Com janela fixa de 10 requisições por segundo, como um cliente consegue 20 requisições em menos de 200 ms?
    Ver resposta explicada

    Resposta: Mandando 10 no fim de uma janela e 10 no começo da seguinte. Cada janela vê só 10. A janela deslizante e o Token Bucket não têm essa brecha.

    Questão 5 (Inventário): A falha foi corrigida na /v2, mas o pentest ainda a encontrou. Onde procurar?
    Ver resposta explicada

    Resposta: Nas versões antigas e endpoints não documentados que continuam no ar, como a /v1. Corrigir uma versão não corrige as outras; o inventário e a desativação formal fecham essa porta.

    Questão 6 (GraphQL): Por que um rate limit que conta requisições HTTP é fraco num GraphQL?
    Ver resposta explicada

    Resposta: Porque o batching coloca muitas operações (por exemplo, centenas de tentativas de login) numa única requisição. O limite precisa contar operações e o custo das consultas.

    Fatos Essenciais, Referências e Próximos Passos

    1. Três autorizações

    Objeto, propriedade e função, sempre no servidor.

    2. Tokens

    Decodificar não é validar: alg, assinatura, exp, aud e iss.

    3. Consumo

    Token Bucket ou janela deslizante; 429 com Retry-After.

    4. Inventário

    A versão esquecida é a que será atacada.

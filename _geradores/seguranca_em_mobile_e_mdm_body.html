Fraude em pagamentos costuma explorar o canal mobile (malware, engenharia social, sessão sequestrada). BYOD sem postura mínima entrega o mesmo canal com menos controle. Trate app e frota como um só risco.

MASVS, MASTG e Riscos Mobile na Prática

O OWASP MASVS (Mobile Application Security Verification Standard) é a régua de requisitos de segurança para apps. O MASTG (Mobile Application Security Testing Guide) orienta como verificar esses requisitos. Use MASVS para desenho e aceite; MASTG para teste — não como diploma de “MASVS completo L2 em tudo”.

Níveis e famílias (visão operacional)

  • L1: baseline para a maioria dos apps (armazenamento, rede, privacidade básica).
  • L2: apps que lidam com dados sensíveis ou risco financeiro (Pix, banking, saúde).
  • R (Resilience): endurecimento contra engenharia reversa e adulteração — complementar, não substituto de L1/L2.

⚠️ Régua, não marketing

“Somos MASVS L2” só vale se houver evidência mapeada requisito → teste (MASTG). Checklist de loja da Apple/Google não substitui verificação de armazenamento e deeplinks.

Android e iOS: Armazenamento, IPC, Rede e Chaves

Armazenamento sensível

  • Android: evitar SharedPreferences/arquivos internos para tokens; preferir EncryptedSharedPreferences / Jetpack Security e, para chaves, Android Keystore (hardware-backed quando disponível).
  • iOS: dados sensíveis no Keychain com kSecAttrAccessibleWhenUnlockedThisDeviceOnly (ou política mais restrita); não guardar segredos em UserDefaults.
  • Logs, crash reporters e analytics: redigir PII e tokens — o “debug” vira vazamento.

IPC, deeplinks e permissões

  • Android intents / exported components: componentes exportados sem validação viram entrada de outro app. Default moderno: não exportar; validar caller e dados.
  • Deeplinks / App Links / Universal Links: tratar parâmetros como entrada não confiável (igual query string web). Autorização sempre no backend.
  • Permissões: peça no momento do uso; explique o porquê; recusa deve degradar com segurança.

Rede

  • Android Network Security Config: bloquear cleartext; pins com cuidado (rotação e backup pins).
  • iOS ATS (App Transport Security): exceções ATS são dívida — documente e limite por domínio.
  • Certificate pinning mal feito trava o app no dia da troca de certificado; planeje operação.

Lab Mental: Percurso de Revisão de um App

Sem emulador neste módulo: percorra o checklist abaixo como se fosse a revisão de um merge request ou um teste guiado pelo MASTG. Anote evidência (tela, trecho, config) para cada passo.

  1. Mapa de superfícies: telas de login, deeplinks, WebViews, SDKs de terceiros.
  2. Auth: onde o token vive? Tempo de vida? Refresh? Logout limpa Keystore/Keychain?
  3. Armazenamento: grep mental por SharedPreferences / UserDefaults / arquivos em claro.
  4. IPC: componentes exportados; intenções recebidas; validação de origem.
  5. Rede: só HTTPS? ATS/NSC? Pinning com plano de rotação?
  6. Backend: o app só “esconde” a regra ou a API reforça (BOLA, rate limit — Estudo 13)?
  7. Build: minificação/ofuscação ajuda resiliência, mas não substitui L1/L2.
  8. Frota: o app exige dispositivo gerenciado / posture (próxima seção) para dados sensíveis?

MDM, UEM e Modelos COPE / BYOD / CYOD

MDM (Mobile Device Management) aplica políticas no dispositivo: enrollment, senha/biometria, criptografia de disco, restrição de loja, remote wipe. UEM (Unified Endpoint Management) estende a ideia a notebooks e outros endpoints — o conceito de posture é o mesmo do Zero Trust (Estudo 08) e do Conditional Access (Estudo 41).

ModeloQuem é donoControle típicoRisco residual
COPEEmpresaMDM forte, perfil de trabalhoPrivacidade do colaborador / shadow IT
CYODEmpresa (escolha limitada)Lista aprovada + MDMCusto; ainda há uso pessoal
BYODColaboradorWork profile / container; MAMWipe parcial; apps pessoais; jailbreak/root

Ciclo operacional

  1. Enrollment: dispositivo entra no domínio de gestão (usuário + identidade corporativa).
  2. Compliance: senha, patch, não-root/jailbreak, disco cifrado — posture para Conditional Access.
  3. Conteúdo: e-mail/VPN/apps só se compliant; senão bloqueio ou acesso degradado.
  4. Saída: offboarding → retire contas e faça wipe (completo ou seletivo no perfil de trabalho).
🔑 Wipe e BYOD

Em BYOD, wipe total do aparelho pessoal sem política clara vira crise jurídica e de RH. Prefira container/perfil de trabalho com wipe seletivo e aceite documentado no enrollment.

EDR no mobile é mais limitado que no desktop (Estudo 10): combine MDM (prevenção/posture) com telemetria de identidade e do app. Não trate “tem MDM” como “tem EDR completo”.

Questões de Fixação e Entrevista

Questão 1 (MASVS): Qual a diferença prática entre MASVS e MASTG?
Ver resposta explicada

Resposta: MASVS lista o que o app deve atender (requisitos). MASTG orienta como testar. Um sem o outro vira marketing ou teste sem critério.

Questão 2 (Armazenamento): Por que UserDefaults / SharedPreferences são péssimos para token de sessão?
Ver resposta explicada

Resposta: Costumam ficar em claro (ou facilmente legíveis) no filesystem do app. Token vai para Keystore (Android) ou Keychain (iOS), com acessibilidade restrita e TTL curto no servidor.

Questão 3 (Deeplink): Um deeplink abre o app já numa tela de transferência Pix. O que validar?
Ver resposta explicada

Resposta: Tratar parâmetros como não confiáveis; exigir sessão autenticada; confirmação e authZ no backend. Deeplink não autoriza pagamento sozinho.

Questão 4 (MDM vs UEM): Em uma frase, o que o UEM acrescenta ao MDM clássico?
Ver resposta explicada

Resposta: Unifica a gestão de posture além do smartphone (ex.: notebooks e outros endpoints), alinhada a Zero Trust / Conditional Access.

Questão 5 (BYOD): O RH pede wipe completo do celular pessoal de um ex-colaborador. O que responder?
Ver resposta explicada

Resposta: Preferir wipe seletivo do perfil/container corporativo e revogação de contas/sessões. Wipe total de BYOD exige base contratual clara; caso contrário, risco jurídico e de confiança.

Questão 6 (Matriz): Para COPE com app de dados financeiros, qual combinação mínima da matriz?
Ver resposta explicada

Resposta: App em linha L2 (Keystore/Keychain, TLS, authZ no servidor) + MDM com compliance e remote wipe + Conditional Access exigindo dispositivo gerenciado.

Questão 7 (Android): Por que android:exported="true" sem necessidade é perigoso?
Ver resposta explicada

Resposta: Outros apps podem invocar o componente (IPC) e enviar dados maliciosos. Só exporte com permissão/validação explícitas.

Questão 8 (iOS): O que uma exceção ATS ampla sinaliza na revisão?
Ver resposta explicada

Resposta: Dívida de comunicação insegura (HTTP ou TLS fraco). Deve ser justificada por domínio, limitada e com plano de remoção — não “ligar ATS off” no projeto todo.

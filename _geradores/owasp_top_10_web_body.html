Introdução: A Aplicação É a Nova Borda

Firewall, WAF e EDR protegem em volta da aplicação, mas não corrigem uma consulta montada com texto do usuário nem um endpoint que entrega o pedido de qualquer cliente a quem pedir. As falhas mais exploradas da web nascem no código, e por isso a correção também está no código. Neste estudo você vai atacar e corrigir a loja online da Ipê Store, o mesmo web-loja01 que você investigou no Estudo 34.

OWASP Top 10:2025

O OWASP Top 10 é a lista de referência dos riscos mais críticos em aplicações web, baseada em dados de testes e na opinião da comunidade. A edição vigente é a OWASP Top 10:2025. Provas e materiais ainda citam a edição de 2021, por isso a tabela mostra de onde veio cada categoria.

Duas mudanças merecem atenção: o SSRF (a aplicação faz requisições para onde o atacante manda), que era uma categoria própria em 2021, passou a fazer parte do controle de acesso; e as categorias novas tratam da cadeia de fornecimento de software (bibliotecas, pacotes, pipelines) e do tratamento de situações excepcionais (erros que vazam detalhes ou deixam o sistema num estado inseguro).

Injeção, XSS, Controle de Acesso e CSRF

Injeção de SQL

Uma SQL injection acontece quando o texto do usuário é concatenado à consulta e passa a ser interpretado como SQL. Com UNION, o atacante junta ao resultado colunas de outra tabela; na injeção cega, a página não mostra dados, mas muda de comportamento conforme a condição injetada; na baseada em tempo, a resposta só demora mais quando a condição é verdadeira. A correção definitiva são as consultas parametrizadas (prepared statements): a estrutura do SQL é fixa e o valor vai separado, então nunca é interpretado como código. Um ORM parametriza por padrão, mas consultas "cruas" escritas dentro dele voltam a ser vulneráveis.

python — consulta vulnerável, consulta correta e checagem de dono 
# Vulnerável: o texto do usuário vira parte do SQL
cur.execute(f"SELECT nome, preco FROM produtos WHERE ativo = 1 AND nome LIKE '%{termo}%'")

# Correto: a estrutura é fixa e o valor vai como parâmetro
cur.execute("SELECT nome, preco FROM produtos WHERE ativo = 1 AND nome LIKE ?", (f"%{termo}%",))

# Controle de acesso por objeto: o pedido precisa ser do usuário logado
pedido = Pedido.get(pedido_id)
if pedido is None or pedido.cliente_id != usuario_atual.id:
    abort(404)

Cross-Site Scripting (XSS)

No XSS, o atacante faz o navegador da vítima executar JavaScript no contexto do site: roubar a sessão, agir em nome do usuário, trocar o formulário de pagamento. No refletido, o código vem na própria requisição (um link manipulado); no armazenado, fica gravado (um comentário) e atinge todos que abrem a página; no baseado em DOM, o próprio JavaScript da página insere o dado sem tratamento.

  • codificação de saída por contexto é a defesa padrão: o texto do usuário vira texto na página (&lt;script&gt;), nunca HTML. Em JavaScript, prefira textContent.
  • sanitização é para quando o usuário precisa mandar HTML (um editor rico): uma biblioteca com allowlist de tags e atributos remove o resto. Filtrar "palavras perigosas" com uma lista de bloqueio sempre deixa passar alguma variação.
  • A Content Security Policy (CSP) é a segunda camada: o navegador recusa scripts inline e de origens não autorizadas, mesmo que a injeção aconteça.

Controle de Acesso Quebrado: BOLA e IDOR

A falha mais comum da lista: o servidor confere quem é o usuário, mas não confere se aquele objeto é dele. BOLA (Broken Object Level Authorization), também chamada de IDOR, é trocar /api/pedidos/1042 por /api/pedidos/1043 e receber o pedido de outra pessoa. A correção é a checagem de dono em toda consulta; IDs aleatórios dificultam adivinhar, mas não corrigem, porque um ID vazado continua funcionando. Para não confirmar que o objeto existe, muitas APIs respondem 404 em vez de 403.

CSRF e Cookies

No CSRF (Cross-Site Request Forgery), um site do atacante faz o navegador da vítima enviar uma requisição para a loja, e o cookie de sessão vai junto. Defesas: cookies com SameSite (Lax ou Strict, que impedem o envio em requisições vindas de outro site), token anti-CSRF nos formulários e confirmação para ações sensíveis. Os atributos HttpOnly (o JavaScript não lê o cookie) e Secure (só vai por HTTPS) completam a proteção da sessão.

📂 Upload sem controle vira webshell

No web-loja01, a pasta de upload aceitava qualquer arquivo e o servidor executava PHP dentro dela: foi assim que um thumb.php virou um terminal para o atacante (Estudo 34). Valide o tipo pelo conteúdo, renomeie os arquivos, guarde-os fora da raiz web ou em armazenamento separado e desligue a execução de scripts na pasta.

Checklist de Segurança de Aplicação Web

Use esta lista numa revisão de código ou antes de publicar uma aplicação. O estado das caixas fica salvo no seu navegador.

Questões de Fixação e Entrevista

Questão 1 (Injeção): Um desenvolvedor propõe remover aspas simples da busca para evitar SQL injection. Por que isso não basta?
Ver resposta explicada

Resposta: Porque há injeções sem aspas (em campos numéricos, por exemplo) e variações de codificação que escapam do filtro. A correção é parametrizar.

Com prepared statements, a estrutura da consulta é fixa e o valor nunca é interpretado como SQL, qualquer que seja o seu conteúdo.

Questão 2 (ORM): A aplicação usa um ORM. Ela está imune a SQL injection?
Ver resposta explicada

Resposta: Não necessariamente. As consultas geradas pelo ORM são parametrizadas, mas trechos de SQL cru escritos dentro dele, montados com texto do usuário, continuam vulneráveis.

Na revisão de código, procure chamadas de consulta crua e ordenações ou nomes de coluna vindos da requisição.

Questão 3 (XSS): Qual é a diferença entre XSS refletido e armazenado, e qual costuma ter impacto maior?
Ver resposta explicada

Resposta: No refletido, o código vem na própria requisição e precisa que a vítima abra um link manipulado; no armazenado, fica gravado e atinge todos que abrem a página. O armazenado costuma ter impacto maior.

Um comentário com script numa página de produto atinge cada cliente que a visitar, inclusive administradores.

Questão 4 (Codificar ou sanitizar): Quando usar codificação de saída e quando usar sanitização?
Ver resposta explicada

Resposta: Codificação sempre que o dado deve aparecer como texto, que é a maioria dos casos. Sanitização com allowlist só quando o usuário precisa enviar HTML formatado.

A CSP é uma camada adicional para os dois casos, não um substituto.

Questão 5 (BOLA): Trocar os IDs sequenciais dos pedidos por UUIDs aleatórios corrige o IDOR?
Ver resposta explicada

Resposta: Não. Dificulta adivinhar, mas um UUID vazado num log, num e-mail ou numa URL compartilhada continua dando acesso.

A correção é conferir, no servidor, se o objeto pertence ao usuário em cada requisição.

Questão 6 (CSRF): Como o atributo SameSite=Lax do cookie de sessão ajuda contra CSRF?
Ver resposta explicada

Resposta: O navegador deixa de enviar o cookie em requisições que mudam estado (como POST) vindas de outro site, então o formulário do atacante chega sem a sessão.

Ações sensíveis ainda devem usar token anti-CSRF e, quando fizer sentido, confirmação do usuário.

Introdução: Pegar a Falha Antes da Produção

Nos Estudos 12 e 13, você explorou uma SQL injection e um mass assignment na loja da Ipê Store depois que já estavam no ar. Corrigir em produção custa caro: incidente, comunicação, correção às pressas. Shift-Left é mover a segurança para o começo do ciclo, de modo que a mesma falha seja apontada no merge request, minutos depois de escrita, por uma ferramenta que roda sozinha a cada mudança. O nome do processo é SSDLC (ciclo de desenvolvimento seguro): requisitos, revisão de código, testes automatizados e verificação antes do deploy.

.github/workflows/seguranca.yml — gates no merge request 
name: seguranca
on: [pull_request]
jobs:
  gates:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0              # histórico completo para o scan de segredos
      # (instalação das ferramentas omitida)
      - name: Segredos
        run: gitleaks detect --source . --redact
      - name: SAST
        run: semgrep scan --config p/python --error
      - name: SCA
        run: pip-audit -r requirements.txt
      - name: Imagem
        run: |
          docker build -t loja:${{ github.sha }} .
          trivy image --severity HIGH,CRITICAL --exit-code 1 loja:${{ github.sha }}

Dependências, Containers e Quality Gates

SBOM: saber o que está dentro

Em dezembro de 2021, o Log4Shell (CVE-2021-44228, CVSS 10.0, na biblioteca log4j-core) obrigou empresas do mundo todo a responder uma pergunta simples: "onde usamos essa biblioteca?". Quem tinha um SBOM (Software Bill of Materials, a lista de componentes de cada software) respondeu em minutos. Os formatos mais usados são o CycloneDX (projeto da OWASP) e o SPDX (Linux Foundation, norma ISO/IEC 5962).

sbom.cdx.json — trecho em CycloneDX 
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "components": [
    { "type": "library", "name": "flask", "version": "3.0.3", "purl": "pkg:pypi/flask@3.0.3" },
    { "type": "library", "name": "pdfgen-lab", "version": "1.2.0", "purl": "pkg:pypi/pdfgen-lab@1.2.0" }
  ]
}

Para priorizar, a gravidade (CVSS) não basta. O EPSS (da FIRST) estima a probabilidade de uma vulnerabilidade ser explorada nos próximos 30 dias, e o catálogo KEV (Known Exploited Vulnerabilities, da CISA) lista as que já estão sendo exploradas. Uma falha alta que está no KEV vem antes de uma crítica que ninguém explora.

Containers

Dockerfile e Kubernetes — o essencial 
# Imagem enxuta e fixada pelo digest (não "latest")
FROM python:3.12-slim@sha256:<digest-conferido>
RUN useradd --create-home --uid 10001 app
COPY --chown=app:app . /app
USER app                      # nunca rodar como root
# segredos chegam em tempo de execução, nunca em ENV ou ARG do Dockerfile

# No Kubernetes (securityContext do container):
#   runAsNonRoot: true
#   readOnlyRootFilesystem: true
#   allowPrivilegeEscalation: false
#   privileged: false

# Assinar a imagem no pipeline e verificar antes do deploy
cosign sign --key cosign.key registry.ipestore.example/loja:1.4.2
cosign verify --key cosign.pub registry.ipestore.example/loja:1.4.2

Imagens distroless trazem só a aplicação e o runtime, sem shell nem gerenciador de pacotes: menos vulnerabilidades e menos ferramentas para um invasor. O projeto Sigstore, com o Cosign, assina imagens com chave própria ou sem chave (keyless, com identidade OIDC e registro público de transparência). O cosign verify antes do deploy garante que só roda o que saiu do pipeline (Estudo 25 trata a mesma ideia como controle de integridade).

Quality gates: quando quebrar o build

  • Um quality gate define o limiar: por exemplo, quebrar com achado alto ou crítico. Limiar baixo demais trava o time em falsos positivos e o pipeline vira algo que todos pulam.
  • Em código antigo, comece com uma baseline: os achados que já existiam são registrados, e o gate bloqueia só o que for novo no merge request. O legado vira um plano de correção à parte.
  • Exceções existem, mas com justificativa, aprovador e validade: é um aceite de risco formal (Estudo 25). Exceção para achado crítico, ou sem data de fim, não é exceção, é abandono.
🔑 Segredo vazado se revoga, não se apaga

Apagar a chave do código num novo commit não a tira do histórico do Git, nem dos clones e forks que já existem. O único remédio é revogar a chave no provedor, gerar outra guardada num cofre e só depois limpar o código. Por isso o scan de segredos olha o histórico inteiro.

    Checklist de DevSecOps

    Use esta lista para avaliar a esteira de um time. O estado das caixas fica salvo no seu navegador.

    Questões de Fixação e Entrevista

    Questão 1 (SAST ou DAST): Qual ferramenta acharia a ausência do cabeçalho Content-Security-Policy, e por quê?
    Ver resposta explicada

    Resposta: O DAST, porque o cabeçalho costuma ser definido na configuração do servidor ou do proxy, fora do código que o SAST analisa. O DAST vê a resposta HTTP real.

    Questão 2 (Segredos): Um desenvolvedor apagou a chave de API no commit seguinte. O incidente acabou?
    Ver resposta explicada

    Resposta: Não. A chave continua no histórico e em todos os clones. É preciso revogá-la no provedor e emitir outra, guardada num cofre.

    Questão 3 (Baseline): Ao ligar o SAST num sistema de dez anos, apareceram 800 achados e o time parou. O que fazer?
    Ver resposta explicada

    Resposta: Registrar os achados atuais como baseline e bloquear só os novos. O legado entra num plano de correção priorizado, começando pelos críticos.

    Questão 4 (SBOM): Saiu uma vulnerabilidade crítica numa biblioteca popular. Como o SBOM ajuda?
    Ver resposta explicada

    Resposta: Com o SBOM de cada aplicação guardado, basta procurar o componente e a versão para saber em minutos quais sistemas são afetados, em vez de abrir projeto por projeto.

    Questão 5 (Containers): Por que fixar a imagem base pelo digest em vez de usar python:latest?
    Ver resposta explicada

    Resposta: Porque latest muda sem aviso: o mesmo Dockerfile gera imagens diferentes a cada build. O digest identifica exatamente o conteúdo, e a atualização vira uma mudança revisada.

    Questão 6 (Exceções): O time pede exceção para uma dependência com falha crítica porque "o fornecedor vai corrigir". Aceitar?
    Ver resposta explicada

    Resposta: Não como exceção de gate. Para crítico, a saída é atualizar, trocar a biblioteca ou mitigar (desligar a função afetada, bloquear a entrada) antes do deploy. Exceções servem para riscos menores, com prazo.

Introdução: Pegar a Falha Antes da Produção

Nos Estudos 12 e 13, você explorou uma SQL injection e um mass assignment na loja da Ipê Store depois que já estavam no ar. Corrigir em produção custa caro: incidente, comunicação, correção às pressas. Shift-Left é mover a segurança para o começo do ciclo, de modo que a mesma falha seja apontada no merge request, minutos depois de escrita, por uma ferramenta que roda sozinha a cada mudança.

Este estudo amarra três camadas: o SSDLC e a maturidade (próxima seção), a cadeia de software (SBOM, SLSA, VEX, containers e gates) e a higiene de secrets no pipeline. A esteira abaixo é o mapa; o detalhe de cada camada vem em seguida.

SSDLC, Security Champions e Maturidade (OWASP SAMM)

Ferramentas na esteira sem processo viram ruído. O SSDLC (Secure Software Development Life Cycle) é o ciclo em que segurança entra em cada fase — não só no scan do merge request.

Fases do SSDLC (visão prática)

  1. Requisitos: dados sensíveis, ameaças de abuso e critérios de aceite de segurança (ex.: “sem segredo no repositório”).
  2. Design: threat modeling leve (pelo menos superfícies de ataque e trust boundaries; STRIDE no Estudo 01).
  3. Implementação: padrões seguros, revisão de código, SAST/segredos no MR.
  4. Verificação: SCA/SBOM, testes, DAST em staging, gates com baseline.
  5. Release: artefato assinado, provenance, só imagem verificada no deploy.
  6. Operação / feedback: monitoramento, correção e lições que voltam aos requisitos.

Security Champion

O Security Champion é alguém do time de produto (não necessariamente AppSec full-time) que conhece os gates, escala riscos e traduz achados em correção. Não substitui o time de AppSec: amplifica cobertura. Sem Champion, o pipeline vira “caixa preta” que o time evita.

OWASP SAMM como régua (não checklist íntegro)

O OWASP SAMM (Software Assurance Maturity Model) organiza práticas em famílias (governança, design, implementação, verificação, operações) com níveis de maturidade. Use-o para diagnosticar onde o programa é fraco (ex.: verificação forte, governança fraca) — não como prova de “SAMM completo” nem como certificação. Este módulo entrega o vocabulário e a ligação com a esteira; um assessment SAMM formal é projeto à parte.

📐 Régua, não diploma

Dizer “estamos no nível 2 de Verification no SAMM” ajuda o roadmap. Dizer “somos SAMM completo” no portal ou no currículo seria promessa falsa — e a rota AppSec deste mapa evita essa frase de propósito.

Dependências, SLSA/VEX, Containers e Quality Gates

SBOM: saber o que está dentro

Em dezembro de 2021, o Log4Shell (CVE-2021-44228, CVSS 10.0, na biblioteca log4j-core) obrigou empresas do mundo todo a responder uma pergunta simples: "onde usamos essa biblioteca?". Quem tinha um SBOM (Software Bill of Materials, a lista de componentes de cada software) respondeu em minutos. Os formatos mais usados são o CycloneDX (projeto da OWASP) e o SPDX (Linux Foundation, norma ISO/IEC 5962).

sbom.cdx.json — trecho em CycloneDX 
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "components": [
    { "type": "library", "name": "flask", "version": "3.0.3", "purl": "pkg:pypi/flask@3.0.3" },
    { "type": "library", "name": "pdfgen-lab", "version": "1.2.0", "purl": "pkg:pypi/pdfgen-lab@1.2.0" }
  ]
}

Para priorizar, a gravidade (CVSS) não basta. O EPSS (da FIRST) estima a probabilidade de uma vulnerabilidade ser explorada nos próximos 30 dias, e o catálogo KEV (Known Exploited Vulnerabilities, da CISA) lista as que já estão sendo exploradas. Uma falha alta que está no KEV vem antes de uma crítica que ninguém explora.

SLSA: níveis de integridade da build

SLSA (Supply-chain Levels for Software Artifacts) descreve quão difícil é adulterar o que você entrega. Na prática, trate os níveis como degraus — não como marketing:

NívelO que exige (visão operacional)Exemplo na esteira
0Nada garantidoBuild no laptop, artefato sem provenance
1Processo documentado + provenance básicaCI gera atestado de “quem buildou o quê”
2Build hospedada, assinatura da provenanceGitHub Actions + Cosign/Sigstore no artefato
3Plataforma isolada, histórico auditávelBuilders não modificáveis pelo autor do código
4Reprodutibilidade e controles máximosRaro fora de fornecedores de alto rigor

Assinatura de imagem (Cosign) e provenance (muitas vezes via in-toto / attestations) respondem: “este binário veio deste commit neste pipeline?”. Sem isso, o SBOM diz o que há dentro, mas não prova a origem.

VEX: quando o CVE não te afeta

Um scanner pode marcar uma CVE na dependência enquanto o código não exerce o caminho vulnerável. VEX (Vulnerability Exploitability eXchange) é o documento/máquina que declara o status (ex.: not_affected, fixed, under_investigation) com justificativa. Sem VEX, o gate ou o time trata todo achado SCA como incidente — ou ignora tudo.

Containers

Dockerfile e Kubernetes — o essencial 
# Imagem enxuta e fixada pelo digest (não "latest")
FROM python:3.12-slim@sha256:<digest-conferido>
RUN useradd --create-home --uid 10001 app
COPY --chown=app:app . /app
USER app                      # nunca rodar como root
# segredos chegam em tempo de execução, nunca em ENV ou ARG do Dockerfile

# No Kubernetes (securityContext do container):
#   runAsNonRoot: true
#   readOnlyRootFilesystem: true
#   allowPrivilegeEscalation: false
#   privileged: false

# Assinar a imagem no pipeline e verificar antes do deploy
cosign sign --key cosign.key registry.ipestore.example/loja:1.4.2
cosign verify --key cosign.pub registry.ipestore.example/loja:1.4.2

Imagens distroless trazem só a aplicação e o runtime, sem shell nem gerenciador de pacotes: menos vulnerabilidades e menos ferramentas para um invasor. O projeto Sigstore, com o Cosign, assina imagens com chave própria ou sem chave (keyless, com identidade OIDC e registro público de transparência). O cosign verify antes do deploy garante que só roda o que saiu do pipeline (Estudo 25 trata a mesma ideia como controle de integridade). Detalhe de runtime de containers/Kubernetes: Estudos 50 e 51.

Quality gates: quando quebrar o build

  • Um quality gate define o limiar: por exemplo, quebrar com achado alto ou crítico. Limiar baixo demais trava o time em falsos positivos e o pipeline vira algo que todos pulam.
  • Em código antigo, comece com uma baseline: os achados que já existiam são registrados, e o gate bloqueia só o que for novo no merge request. O legado vira um plano de correção à parte.
  • Exceções existem, mas com justificativa, aprovador e validade: é um aceite de risco formal (Estudo 25). Exceção para achado crítico, ou sem data de fim, não é exceção, é abandono.
  • Combine gate de SCA com VEX: “CVE presente no SBOM, mas not_affected documentado” pode passar; “crítico no KEV sem mitigação” não.

Secrets no Pipeline: Scan, Revogação e Cofre

Segredo no Git é incidente de identidade, não “dívida técnica”. O scan no merge request é necessário; o scan no histórico (fetch-depth: 0 + Gitleaks) é o que pega o commit antigo que ninguém reviu.

🔑 Segredo vazado se revoga, não se apaga

Apagar a chave do código num novo commit não a tira do histórico do Git, nem dos clones e forks que já existem. O único remédio é revogar a chave no provedor, gerar outra guardada num cofre e só depois limpar o código.

Onde o segredo deveria viver

  • Cofre / secret store (ou secrets do provedor de CI) injetados em runtime — não em arquivos versionados.
  • OIDC federado no CI: o job assume uma identidade de curta duração no provedor de nuvem, em vez de access keys estáticas no repositório.
  • Rotação e menor privilégio: token de deploy não precisa de permissão de admin da conta.

Anti-padrões

  • ENV / ARG com senha no Dockerfile (fica em camadas e no histórico do registry).
  • Imprimir secrets em logs do pipeline “para debug”.
  • PATs e cloud keys de longa duração colados em variáveis do repositório sem rotação.
  • Acreditar que “só o time privado vê o repo” — forks, backups e ex-colaboradores existem.

O Estudo 03 (criptografia) e os módulos de nuvem/IAM cobrem chaves e identidade em profundidade; aqui o foco é não deixar o pipeline ser o vazador.

Checklist de DevSecOps

Use esta lista para avaliar a esteira de um time. O estado das caixas fica salvo no seu navegador.

Questões de Fixação e Entrevista

Questão 1 (SAST ou DAST): Qual ferramenta acharia a ausência do cabeçalho Content-Security-Policy, e por quê?
Ver resposta explicada

Resposta: O DAST, porque o cabeçalho costuma ser definido na configuração do servidor ou do proxy, fora do código que o SAST analisa. O DAST vê a resposta HTTP real.

Questão 2 (Segredos): Um desenvolvedor apagou a chave de API no commit seguinte. O incidente acabou?
Ver resposta explicada

Resposta: Não. A chave continua no histórico e em todos os clones. É preciso revogá-la no provedor e emitir outra, guardada num cofre.

Questão 3 (Baseline): Ao ligar o SAST num sistema de dez anos, apareceram 800 achados e o time parou. O que fazer?
Ver resposta explicada

Resposta: Registrar os achados atuais como baseline e bloquear só os novos. O legado entra num plano de correção priorizado, começando pelos críticos.

Questão 4 (SBOM): Saiu uma vulnerabilidade crítica numa biblioteca popular. Como o SBOM ajuda?
Ver resposta explicada

Resposta: Com o SBOM de cada aplicação guardado, basta procurar o componente e a versão para saber em minutos quais sistemas são afetados, em vez de abrir projeto por projeto.

Questão 5 (Containers): Por que fixar a imagem base pelo digest em vez de usar python:latest?
Ver resposta explicada

Resposta: Porque latest muda sem aviso: o mesmo Dockerfile gera imagens diferentes a cada build. O digest identifica exatamente o conteúdo, e a atualização vira uma mudança revisada.

Questão 6 (Exceções): O time pede exceção para uma dependência com falha crítica porque "o fornecedor vai corrigir". Aceitar?
Ver resposta explicada

Resposta: Não como exceção de gate. Para crítico, a saída é atualizar, trocar a biblioteca ou mitigar (desligar a função afetada, bloquear a entrada) antes do deploy. Exceções servem para riscos menores, com prazo.

Questão 7 (SSDLC): O time só tem Semgrep no MR e chama isso de “SSDLC completo”. O que falta no ciclo?
Ver resposta explicada

Resposta: SSDLC cobre requisitos, design, verificação, release e feedback operacional — não só SAST. Faltam, no mínimo, ameaças no design, SCA/SBOM, gates de release e retorno de incidentes aos requisitos. Um Security Champion ajuda a sustentar o processo.

Questão 8 (SLSA): Qual a diferença prática entre ter SBOM e atingir um nível SLSA ≥ 2?
Ver resposta explicada

Resposta: O SBOM lista componentes. SLSA ≥ 2 exige build hospedada com provenance assinada — prova de origem do artefato (ex.: Cosign/in-toto), não só o inventário.

Questão 9 (VEX): O SCA marca CVE numa lib transitiva; o time alega que o código nunca chama a API vulnerável. O que falta para o gate confiar nisso?
Ver resposta explicada

Resposta: Um status VEX (ex.: not_affected) com justificativa revisável. Afirmação oral não substitui o documento que o processo de risk acceptance / gate consome.

Questão 10 (SAMM / Champion): Para que serve o OWASP SAMM neste módulo, e o que um Security Champion não substitui?
Ver resposta explicada

Resposta: SAMM é régua de maturidade (governança, design, implementação, verificação, ops), não diploma de “SAMM completo”. O Champion amplifica o time de produto; não substitui AppSec especializado nem um assessment formal.

Fatos Essenciais, Referências e Próximos Passos

1. Shift-Left + SSDLC

A falha no MR custa minutos; SSDLC cobre o ciclo inteiro, não só o scanner.

2. Ferramentas

SAST no código, SCA nas dependências, DAST na aplicação, segredos no histórico.

3. Cadeia de software

SBOM + SLSA/provenance + VEX; imagem enxuta e assinatura verificada.

4. Secrets

Revogar, cofre/OIDC, nunca ENV/ARG nem PAT eterno no repo.

5. Gates

Limiar por severidade, baseline para o legado e exceções com prazo.

6. Champion / SAMM

Champion no time; SAMM como régua de maturidade, não como diploma.

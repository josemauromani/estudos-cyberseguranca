Introdução: O Bucket Que Passou na Revisão

A Ipê Store descreve toda a sua conta AWS em Terraform: buckets, redes, bancos, balanceadores e a trilha de auditoria. No pull request #318, o time fiscal criou o bucket das notas fiscais. A revisora leu o diff do HCL, viu um bloco de Block Public Access e aprovou. Ninguém reparou que duas das quatro chaves estavam em false "provisoriamente". Três dias depois, o CSPM do Estudo 21 apontou o bucket como exposto. Nada vazou, mas por sorte. A pergunta deste módulo é outra: por que uma configuração proibida conseguiu ser criada? Aqui você aprende a ler o plano do Terraform em vez do diff, a escrever políticas como código que barram o plano antes do apply, a proteger o state e a descobrir quando o ambiente real deixou de ser o que o código diz.

Plano, Políticas como Código, State e Drift

Ler o plano, não só o diff

O diff do HCL mostra o que o autor escreveu; o plano mostra o que vai acontecer. Um módulo com padrão inseguro, uma variável vinda de outro arquivo ou um count que multiplica recursos não aparecem no diff. Por isso a revisão automatizada lê o plano em JSON: terraform plan -out=plano.tfplan grava o plano, e terraform show -json plano.tfplan o converte. Nele, a lista resource_changes traz cada recurso com address, type, change.actions (create, update, delete; uma substituição aparece como delete e create), change.before, change.after e after_unknown (o que só será conhecido no apply). O bloco configuration mostra as expressões do código: se um atributo veio de um literal (constant_value) ou de uma referência.

bash — gerar o plano e ler as mudanças de risco (saída ilustrativa) 
$ terraform plan -out=plano.tfplan
$ terraform show -json plano.tfplan > plano.json

# Quais recursos o plano cria, muda ou substitui?
$ jq -r '.resource_changes[] | select(.change.actions != ["no-op"])
         | "\(.change.actions | join("/"))  \(.address)"' plano.json
create  aws_s3_bucket.notas_fiscais
create  aws_s3_bucket_public_access_block.notas_fiscais
update  aws_cloudtrail.principal
delete  aws_security_group.legado_ftp

# O que muda na trilha de auditoria?
$ jq '.resource_changes[] | select(.address=="aws_cloudtrail.principal")
      | {antes: .change.before.enable_logging, depois: .change.after.enable_logging}' plano.json
{ "antes": true, "depois": false }
⚠️ O plano em JSON também é segredo

Valores marcados como sensitive aparecem como (sensitive value) na tela, mas o terraform show -json os traz em claro, apenas sinalizados em after_sensitive. O arquivo do plano guardado como artefato do pipeline precisa da mesma proteção do state: retenção curta e acesso restrito.

Varredura de IaC e policy-as-code

Há duas camadas complementares. A varredura de IaC roda regras prontas sobre o código ou o plano e cobre o básico em minutos. As políticas como código (policy-as-code) traduzem as regras da própria empresa ("todo bucket confidencial usa a nossa chave KMS", "nenhuma porta administrativa para a internet") em código versionado, testado e revisado como qualquer outro.

Rego — política que reprova porta administrativa aberta (policy/rede.rego) 
package terraform.rede

portas_admin := [22, 3389]

deny contains msg if {
  rc := input.resource_changes[_]
  rc.type == "aws_security_group"
  some acao in rc.change.actions
  acao in {"create", "update"}          # apagar recurso inseguro não é bloqueado
  regra := rc.change.after.ingress[_]
  regra.cidr_blocks[_] == "0.0.0.0/0"
  some porta in portas_admin
  regra.from_port <= porta             # faixas como 20-25 também contam
  porta <= regra.to_port
  msg := sprintf("%s: porta %d aberta para a internet", [rc.address, porta])
}

# No pipeline:
#   conftest test plano.json --policy policy/
#   checkov -f plano.json --framework terraform_plan

Módulos aprovados: o caminho seguro é o mais curto

Política que só reprova gera atrito; módulos aprovados reduzem o atrito. A equipe de plataforma publica módulos internos com versão fixada (source apontando para o registro interno e version = "~> 3.2") em que a criptografia, o Block Public Access, o log e as tags de dono já vêm ligados e não são parâmetros. O time do produto pede um bucket e recebe um bucket seguro. A política continua lá para pegar quem cria o recurso "na mão", fora do módulo.

Exceções com prazo e responsável

Sempre haverá um caso legítimo que viola uma regra: um bucket público de imagens até a migração para CDN, uma regra provisória durante uma migração. O erro é resolver com um comentário de supressão no código (#checkov:skip=...) que nunca mais sai. Uma exceção bem feita é um registro central, fora do código do produto, com quatro campos: qual política, qual recurso, quem é o responsável pelo risco e até quando vale. Ao vencer o prazo, a regra volta a reprovar sozinha, e alguém precisa decidir de novo. Um teto de prazo (90 dias, por exemplo) impede a exceção "até 2099".

State: o arquivo mais sensível do repositório

O state guarda todos os atributos de cada recurso, inclusive os sensíveis, em texto claro: a senha do banco, o result de um random_password, o secret de uma chave de acesso. Marcar uma variável ou saída como sensitive = true só a esconde da tela e dos logs; no state ela continua em claro. O OpenTofu oferece criptografia do state no cliente; no Terraform, a proteção vem do backend e do acesso a ele:

  • Backend remoto (bucket S3 dedicado, numa conta separada de preferência), nunca o terraform.tfstate no notebook nem no Git.
  • Criptografia com encrypt = true e chave KMS própria (kms_key_id), cuja política de chave restringe quem decifra.
  • Bloqueio: use_lockfile = true no backend S3 (Terraform 1.10 em diante); versões anteriores usavam uma tabela DynamoDB, hoje em descontinuação. Sem bloqueio, dois applies simultâneos corrompem o state.
  • Versionamento do bucket, para voltar a um state anterior, e acesso só para a role do pipeline e o acesso de emergência.
  • Tirar o segredo do state quando possível: manage_master_user_password = true faz o RDS guardar a senha no Secrets Manager; chaves de acesso de longa duração dão lugar a roles e OIDC.
HCL — backend remoto com criptografia e bloqueio 
terraform {
  backend "s3" {
    bucket       = "ipe-terraform-state-prod"      # conta dedicada, versionamento ligado
    key          = "loja/prod/terraform.tfstate"
    region       = "sa-east-1"
    encrypt      = true
    kms_key_id   = "alias/ipe-terraform-state"
    use_lockfile = true                            # bloqueio nativo no S3
  }
}

resource "aws_db_instance" "pedidos" {
  # ...
  username                    = "app_pedidos"
  manage_master_user_password = true   # a senha fica no Secrets Manager, fora do state
}

Drift: quando o ambiente diverge do código

Drift é a diferença entre o que o código declara e o que existe na conta. Ele nasce de mudanças feitas pelo console ou pela CLI durante um incidente, de um fornecedor com acesso, de automações fora do Terraform. O comando terraform plan -refresh-only mostra o que mudou nos recursos que o Terraform gerencia, sem propor alterações; agendado no pipeline (diariamente, por exemplo), vira um detector de drift. Para cada divergência há duas saídas: reverter (o próximo apply devolve o valor do código) ou incorporar (atualizar o HCL para refletir a mudança, e o novo código passa pelas mesmas políticas). Recursos criados inteiramente fora do Terraform não aparecem no plan: precisam ser trazidos com um bloco import ou o comando terraform import, ou apagados, e só um inventário ou o CSPM do Estudo 21 os encontra.

🚨 Política no pipeline não adianta se o apply sai do notebook

Se cada engenheiro tem credencial de administrador e roda terraform apply do próprio terminal, nenhuma política é obrigatória. O desenho seguro: o pipeline obtém credenciais temporárias por OIDC (sem chave de longa duração guardada no CI); a role de plan só lê; a role de apply só é assumida pelo pipeline, a partir do branch principal e após aprovação; o console de produção fica só leitura, com acesso de emergência registrado. É a mesma separação de deveres do Estudo 22, aplicada à infraestrutura.

Checklist de IaC Segura

Use esta lista ao revisar um repositório de Terraform ou o pipeline que o aplica. O estado das caixas fica salvo no seu navegador.

Questões de Fixação e Entrevista

Questão 1 (Plano x diff): O pull request só muda a versão de um módulo interno de bucket, de 3.1 para 3.2. O diff tem uma linha. Por que a política deve ler o plano, e não o diff?
Ver resposta explicada

Resposta: Porque a mudança real está dentro do módulo. Se a versão 3.2 mudou um padrão (por exemplo, desligou o Block Public Access), o diff de uma linha não mostra nada, mas o plano mostra o aws_s3_bucket_public_access_block com false em change.after. O plano resolve módulos, variáveis e count; é o que vai acontecer de fato no apply.

Questão 2 (State): O time usa random_password para a senha do banco e marcou a saída como sensitive = true. Um colega diz que, assim, a senha não está em lugar nenhum em claro. Está certo?
Ver resposta explicada

Resposta: Não. sensitive só esconde o valor da saída do terminal e dos logs. O result do random_password e o password do banco ficam em claro no state, e também no plano em JSON. A proteção é tratar o state como cofre (backend remoto criptografado com KMS, acesso restrito, versionamento) e, quando possível, tirar o segredo dele com manage_master_user_password = true.

Questão 3 (Exceção): O time da vitrine precisa servir imagens direto de um bucket público por dois meses, até migrar para CDN. A política de bucket público reprova o plano. Qual é a forma correta de seguir?
Ver resposta explicada

Resposta: Registrar uma exceção para aquele recurso e aquela política, com responsável nomeado, justificativa e expiração dentro do teto (por exemplo, 60 dias). Desligar a política para todos ou pôr um #checkov:skip sem prazo no código são as respostas erradas: a primeira libera qualquer bucket; a segunda vira permanente. Quando a exceção vence, o plano volta a ser reprovado e força a decisão.

Questão 4 (Drift): O terraform plan -refresh-only da madrugada mostra uma regra de entrada 3389 a partir de 0.0.0.0/0 num security group, criada pelo console por um fornecedor. O fornecedor pede para "colocar no código para não dar mais alerta". O que fazer?
Ver resposta explicada

Resposta: Reverter, não incorporar. A mudança viola a política de porta administrativa; incorporá-la ao HCL faria o próximo plano ser reprovado, como deve ser. Reverta com um apply do código (ou remova a regra), trate o caso como incidente até saber quem usou o acesso e ofereça ao fornecedor um caminho controlado (Session Manager ou VPN). Depois, revise por que alguém de fora tinha permissão de escrita no console.

Questão 5 (Recurso fora do Terraform): O CSPM achou um security group com RDP aberto que não aparece em nenhum plano, nem no de drift. Por quê, e como resolver?
Ver resposta explicada

Resposta: O Terraform só compara o que está no state; um recurso criado inteiramente pelo console não é gerenciado e, portanto, não gera drift. É exatamente o papel do CSPM do Estudo 21 complementar a IaC. A solução é decidir: apagar o recurso, ou trazê-lo para o código com um bloco import (ou terraform import), quando ele passa a ser avaliado pelas políticas, e corrigido.

Questão 6 (Credenciais do pipeline): As políticas rodam no pipeline, mas três engenheiros têm chave de administrador e às vezes rodam terraform apply do notebook "para ir mais rápido". Qual é o problema e a correção?
Ver resposta explicada

Resposta: A política vira opcional: quem aplica do notebook passa por fora dela, sem revisão, e ainda arrisca dois applies simultâneos no mesmo state. A correção é tornar o pipeline o único caminho: credencial por OIDC, role de apply assumível só pelo pipeline a partir do branch principal, chaves pessoais de administrador removidas e acesso de emergência registrado e revisado.

Questão 7 (Apagar é bloqueado?): O plano apaga um security group antigo que tinha FTP aberto para a internet. A política de rede deveria reprovar esse plano?
Ver resposta explicada

Resposta: Não. A política avalia o estado depois da mudança (change.after) para ações create e update; num delete, o after é nulo, e remover algo inseguro é uma melhoria. O cuidado é o inverso: uma substituição aparece como delete e create, e o recurso novo precisa ser avaliado como qualquer criação.

Fatos Essenciais, Referências e Próximos Passos

1. Ordem

Plano antes do apply, política antes do plano: o pipeline lê o plano em JSON e reprova o que a empresa proíbe antes que exista.

2. Segredos

State do Terraform contém segredos em claro: backend remoto, criptografia com KMS, bloqueio, versionamento e acesso restrito.

3. Exceções

Policy-as-code com exceções com prazo e responsável: ao vencer, a regra volta a reprovar sozinha.

4. Drift

Drift: o ambiente diverge do código. Detecte com plan -refresh-only agendado; reverta o que viola política, incorpore o resto.

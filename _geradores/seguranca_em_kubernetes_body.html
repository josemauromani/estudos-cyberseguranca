Seção 01

Introdução: O Token Que Vinha Junto com o Pod

Depois do incidente do Estudo 50, a Ipê Store levou a API de pedidos para um cluster Kubernetes, com a imagem endurecida: distroless, usuário não root, sem docker.sock. Meses depois, uma nova falha na aplicação deu de novo um shell dentro do contêiner. Desta vez não havia socket nem --privileged, mas havia um arquivo que o Kubernetes monta em todo pod por padrão: /var/run/secrets/kubernetes.io/serviceaccount/token, a credencial da conta de serviço da API. Com ela, o invasor falou com o API server como se fosse a aplicação. A conta podia ler Secrets do namespace; num deles estava o token de outra conta, que podia criar pods no cluster inteiro. Três saltos depois, o invasor era administrador do cluster. Este módulo ensina a ler o RBAC como um mapa de caminhos, a barrar pods perigosos na admissão e a limitar o que cada pod alcança na rede.

☸️ Pergunta-chave do módulo

Uma conta de serviço comprometida consegue chegar a administrador do cluster?

🧭 O que vem do Estudo 50 e do Estudo 04

O Estudo 50 tratou um contêiner isolado: imagem, build e as opções do docker run. Aqui as mesmas proteções reaparecem como campos do manifesto (privileged, hostPID, capabilities, seccompProfile), e a novidade é o plano de controle: quem pode pedir o quê ao API server. Do Estudo 04 vêm o modelo RBAC, o menor privilégio e a ideia de que token é credencial; este módulo não repete o RBAC genérico, e sim os verbos do Kubernetes que transformam uma permissão pequena em administração do cluster.

No MITRE ATT&CK, três técnicas resumem o que se tenta fazer num cluster: T1613 Container and Resource Discovery (listar pods, segredos e permissões com a credencial obtida; kubectl auth can-i --list é a primeira pergunta), T1609 Container Administration Command (executar comandos em contêineres pelo pods/exec ou pelo kubelet) e T1611 Escape to Host (um pod privilegiado ou com hostPath que entrega o nó). Cada uma depende de uma configuração que a equipe controla: um binding largo demais, um pod admitido sem restrição, uma rede plana.

Seção 02

RBAC, Pod Security, NetworkPolicy e Segredos

RBAC: papéis, bindings e escopo

O RBAC do Kubernetes tem quatro objetos. Role e ClusterRole listam regras (verbos sobre recursos); RoleBinding e ClusterRoleBinding ligam um papel a sujeitos (usuários, grupos ou contas de serviço). O escopo vem do binding: um RoleBinding vale só no namespace dele, mesmo quando aponta para uma ClusterRole; um ClusterRoleBinding vale no cluster inteiro. O erro mais comum é usar ClusterRoleBinding "porque era mais fácil" para algo que só precisava de um namespace. Não existe regra de negação: as permissões só se somam.

PermissãoPor que equivale a mais privilégio
create pods (ou Deployments, Jobs, DaemonSets)O pod pode declarar qualquer conta de serviço do namespace e recebe o token dela; também pode pedir hostPath ou privileged, se a admissão deixar.
get secrets / list secretsLê senhas, chaves e os tokens de longa duração guardados em Secrets. list devolve o conteúdo, não só os nomes.
create pods/execEntra num pod que já roda com uma conta mais forte e usa o token montado nele (T1609).
bind em ClusterRoles + create em ClusterRoleBindingsLiga qualquer papel, inclusive cluster-admin, a si mesmo. Sem bind, o API server só aceita bindings de permissões que você já tem.
escalate + update em ClusterRolesEdita o próprio papel e acrescenta permissões que não possui.
impersonateEnvia requisições como outro usuário, grupo ou conta de serviço.
Curinga * em verbos ou recursosInclui tudo o que existe hoje e tudo o que for criado depois (CRDs novos, subrecursos). * em * no cluster é cluster-admin.
bash — auditar o que uma conta de serviço pode fazer (saída ilustrativa) 
# O que a conta da API pode fazer no namespace dela?
$ kubectl auth can-i --list --as=system:serviceaccount:pedidos:sa-api-pedidos -n pedidos
Resources        Verbs
configmaps       [get list]
secrets          [get list]          # isto abre o primeiro salto
pods/exec        [create]            # e isto, o segundo caminho

# Perguntas diretas, uma por verbo perigoso
$ kubectl auth can-i create pods --all-namespaces --as=system:serviceaccount:pedidos:sa-migracoes
yes                                  # ClusterRoleBinding onde bastava um RoleBinding
$ kubectl auth can-i bind clusterroles --as=system:serviceaccount:ci:sa-deployer
yes

# Quem está ligado ao cluster-admin?
$ kubectl get clusterrolebindings -o wide | grep cluster-admin

Conta de serviço: o token é credencial

Todo pod roda com uma conta de serviço (a default do namespace, se nada for dito), e o kubelet monta o token dela dentro do pod. Quem lê esse arquivo fala com o API server com as permissões da conta. Três práticas reduzem o estrago:

  • automountServiceAccountToken: false no pod ou na conta, quando a aplicação não fala com a API do Kubernetes (a maioria não fala).
  • Token projetado, emitido pela API TokenRequest: tem audiência, expira (uma hora, por padrão, renovado pelo kubelet) e morre com o pod. Desde a versão 1.24, o Kubernetes não cria mais Secrets de token de longa duração automaticamente; os que sobraram de clusters antigos não expiram e devem ser apagados.
  • Uma conta por aplicação, com RoleBinding no namespace dela, e nenhuma permissão na conta default.

Pod Security Standards e Pod Security Admission

Os Pod Security Standards definem três níveis acumulativos, e o Pod Security Admission (controlador embutido desde a versão 1.25) os aplica por namespace, com rótulos. O modo enforce rejeita o pod; audit registra no log de auditoria; warn devolve um aviso ao kubectl. A estratégia usual é ligar warn e audit em restricted, corrigir o que aparece e só depois subir o enforce.

NívelO que exigePara quem
privilegedNada: sem restriçãoComponentes de sistema e agentes de nó, em namespace próprio e com exceção documentada
baselineProíbe o que entrega o nó: privileged, hostNetwork, hostPID, hostIPC, hostPath, capabilities fora da lista padrão, seccomp UnconfinedPiso mínimo para qualquer aplicação
restrictedTudo do baseline e mais: runAsNonRoot: true, allowPrivilegeEscalation: false, capabilities.drop: [ALL] (só NET_BIND_SERVICE pode voltar), seccompProfile RuntimeDefault ou LocalhostMeta para as aplicações da empresa
YAML — namespace com Pod Security Admission e pod que atende ao restricted 
apiVersion: v1
kind: Namespace
metadata:
  name: pedidos
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
---
apiVersion: v1
kind: Pod
metadata:
  name: api-pedidos
  namespace: pedidos
spec:
  serviceAccountName: sa-api-pedidos
  automountServiceAccountToken: false     # a API não fala com o API server
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: api
      image: registro.ipe.example/pedidos/api:2.4.1
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: [ALL]
⚠️ Admissão olha o pod, não o RBAC

O Pod Security Admission avalia também os pods criados por Deployments e Jobs, mas não impede ninguém de criar pods que atendem ao nível exigido usando outra conta de serviço do namespace. Pod Security e RBAC se completam: um decide como o pod pode ser; o outro, quem pode criá-lo e com qual identidade.

NetworkPolicy: negar por padrão e liberar o necessário

Sem nenhuma política, todo pod fala com todo pod do cluster, em qualquer porta. Uma NetworkPolicy seleciona pods de um namespace e, a partir daí, eles só aceitam (Ingress) ou só iniciam (Egress) o que alguma política liberar; as políticas se somam, sem ordem e sem regra de negação. Por isso o padrão é negar por padrão em cada namespace e liberar fluxo por fluxo. A política só funciona se o CNI a aplicar: Calico e Cilium aplicam; alguns plugins simples ignoram em silêncio. Lembre também da saída: um pod comprometido sem regra de Egress fala com a internet e com tudo o que não tem política.

YAML — negar por padrão em pedidos e liberar a saída da API 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: negar-tudo
  namespace: pedidos
spec:
  podSelector: {}              # todos os pods do namespace
  policyTypes: [Ingress, Egress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: saida-api-pedidos
  namespace: pedidos
spec:
  podSelector:
    matchLabels: {app: api-pedidos}
  policyTypes: [Egress]
  egress:
    - to:
        - podSelector: {matchLabels: {app: postgres}}
      ports: [{port: 5432, protocol: TCP}]
    - to:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}
          podSelector: {matchLabels: {k8s-app: kube-dns}}
      ports: [{port: 53, protocol: UDP}, {port: 53, protocol: TCP}]

Secrets, admissão, auditoria e benchmark

  • Secrets no etcd: por padrão, um Secret é só base64 no etcd. Ligue a criptografia em repouso com EncryptionConfiguration, de preferência com um provedor KMS (a chave fica fora do cluster), restrinja get/list/watch em secrets e considere um cofre externo com sincronização.
  • API server e kubelet: API server fora da internet ou atrás de lista de origem, autenticação federada com MFA para humanos (Estudo 04), kubelet sem acesso anônimo e com autorização Webhook.
  • Controle de admissão: além do Pod Security Admission, políticas próprias com Kyverno, OPA Gatekeeper ou a nativa ValidatingAdmissionPolicy (CEL) exigem imagem assinada e do registro da empresa, limites de recurso e rótulos de dono. É aqui que a assinatura do Estudo 50 passa a ser verificada antes de rodar.
  • Logs de auditoria: a política de auditoria do API server registra quem pediu o quê. Alerte sobre criação de ClusterRoleBinding, pods/exec, leitura de secrets por conta de serviço, uso de impersonate e pods rejeitados pela admissão.
  • CIS Kubernetes Benchmark: lista de controles do plano de controle, dos nós e das políticas; o kube-bench verifica muitos deles de forma automatizada. O guia de hardening da NSA e da CISA (Kubernetes Hardening Guidance) cobre os mesmos temas com foco em ameaças.
🚨 Contas esquecidas são caminho pronto

Contas de ferramentas desativadas com ClusterRoleBinding para cluster-admin e Secrets de token que nunca expiram são o achado mais comum em revisões de cluster. Revise periodicamente quem está ligado a papéis administrativos, como no recadastramento de acessos privilegiados.

            Seção 05
            
Questões de Fixação e Entrevista

        


        

            

                Questão 1 (create pods): Uma conta de serviço tem apenas create em pods no namespace pedidos, sem acesso a secrets. Um colega diz que é uma permissão inofensiva. Por que não é?
            

            

                Ver resposta explicada
                

                    
Resposta: Quem cria um pod escolhe com qual conta de serviço ele roda, e o kubelet monta o token dessa conta dentro dele. Logo, create pods num namespace vale as permissões da conta mais forte desse namespace; se a admissão não barrar, o pod ainda pode pedir hostPath ou privileged e chegar ao nó. O mesmo vale para quem cria Deployments, Jobs ou DaemonSets.

                

            

        


        

            

                Questão 2 (Escopo): O pipeline precisa criar RoleBindings no namespace das aplicações. Hoje ele tem um ClusterRoleBinding com create em clusterrolebindings e bind em clusterroles. Qual o risco e qual a correção?
            

            

                Ver resposta explicada
                

                    
Resposta: Com bind e permissão de criar ClusterRoleBinding, a conta liga o cluster-admin a si mesma: quem rouba o token do pipeline vira administrador. A correção é um RoleBinding no namespace das aplicações, só com rolebindings, e de preferência com bind limitado a papéis nomeados (resourceNames). O pipeline continua funcionando; o caminho até o cluster deixa de existir.

                

            

        


        

            

                Questão 3 (Pod Security): O namespace relatorios passou a exigir restricted e o deploy do worker começou a falhar, embora o securityContext do pod tenha runAsNonRoot: true. O que procurar?
            

            

                Ver resposta explicada
                

                    
Resposta: O securityContext de cada contêiner sobrepõe o do pod. Um contêiner com runAsNonRoot: false, allowPrivilegeEscalation ausente ou true, ou capabilities sem drop: [ALL] viola o nível sozinho. A mensagem do Pod Security Admission diz qual campo e qual contêiner; o certo é corrigir o manifesto, não rebaixar o namespace para baseline.

                

            

        


        

            

                Questão 4 (NetworkPolicy): O time aplicou negar entrada por padrão em todos os namespaces e liberou os fluxos necessários. O pentest ainda mostrou que a API comprometida enviava dados para fora. O que faltou?
            

            

                Ver resposta explicada
                

                    
Resposta: Faltou a saída. Política só de Ingress protege quem recebe; o pod comprometido continua iniciando conexões para a internet e para tudo o que não tem política (como o namespace do controlador de ingress). Negue Egress por padrão nos namespaces de aplicação e libere só as dependências, sem esquecer o DNS (porta 53 para o kube-dns), ou nada resolve nome.

                

            

        


        

            

                Questão 5 (Token): A vitrine não usa a API do Kubernetes. Mesmo assim, a conta dela tem só leitura de configmaps. Vale desligar o token montado?
            

            

                Ver resposta explicada
                

                    
Resposta: Sim. Token de conta de serviço é credencial: com ele, o invasor faz descoberta no cluster (T1613), e qualquer permissão acrescentada à conta no futuro passa a valer para quem o roubou. automountServiceAccountToken: false tira a credencial do alcance de uma falha na aplicação a custo zero.

                

            

        


        

            

                Questão 6 (Secrets): Um auditor diz que os Secrets do cluster estão "criptografados porque estão em base64". Você concorda?
            

            

                Ver resposta explicada
                

                    
Resposta: Não. Base64 é codificação, não criptografia. Sem EncryptionConfiguration, o etcd guarda os Secrets em claro, e um backup do etcd é uma cópia de todas as credenciais. A proteção tem três partes: criptografia em repouso com KMS, RBAC estreito em get/list/watch de secrets e acesso ao etcd restrito ao API server, com TLS.

                

            

        


        

            

                Questão 7 (Correção mínima): Na revisão, você acha uma conta de migração com ClusterRoleBinding para criar pods, usada só no namespace pedidos. Removê-la quebra o caminho até o cluster-admin, mas também as migrações. Qual a melhor saída?
            

            

                Ver resposta explicada
                

                    
Resposta: Restringir em vez de remover: trocar o ClusterRoleBinding por um RoleBinding em pedidos. As migrações continuam; a conta deixa de criar pods em kube-system, ci e nos outros namespaces, que era o salto do caminho. Em seguida, limpe as outras pontas: contas esquecidas com cluster-admin, Secrets de token de longa duração e o binding de depuração que deixou pods/exec para a API.

                

            

        

    


    
    

        

            Seção 06
            
Fatos Essenciais, Referências e Próximos Passos

        


        

            

                
1. Verbos

                
RBAC: create pods, bind e escalate são privilégio, assim como get secrets, pods/exec, impersonate e o curinga.

            

            

                
2. Admissão

                
Pod Security Standards: privileged, baseline, restricted, aplicados por namespace pelo Pod Security Admission.

            

            

                
3. Rede

                
NetworkPolicy com negação por padrão, na entrada e na saída, e liberação fluxo a fluxo, incluindo o DNS.

            

            

                
4. Identidade

                
Token de conta de serviço é credencial: desligue o montado quando não é usado e prefira o token projetado.
